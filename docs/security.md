# THE VISA GATE — Security Architecture & Authentication Specification

## 1. Multi-Tiered Access & Entry Separation

The system implements 3 completely distinct authentication and portal experiences:

```
                            ┌─────────────────────────────────┐
                            │    THE VISA GATE ROUTER         │
                            └────────────────┬────────────────┘
                                             │
             ┌───────────────────────────────┼───────────────────────────────┐
             │                               │                               │
   ┌─────────▼──────────┐          ┌─────────▼──────────┐          ┌─────────▼──────────┐
   │   PUBLIC WEBSITE   │          │   CLIENT PORTAL    │          │  EMPLOYEE PORTAL   │
   │  (Unauthenticated) │          │(Passport Number ID)│          │ (Staff & Admins)   │
   └─────────┬──────────┘          └─────────┬──────────┘          └─────────┬──────────┘
             │                               │                               │
    Open Corporate Pages             Read-Only Tracking               Role-Guarded Cockpit
    Services & Inquiries             Masked Identifiers               2FA/MFA Enforced
    No Admin/Staff links             No Upload / Edit Forms           Full Operation Suite
```

### A. Public Corporate Website
* Open to visitors worldwide.
* Zero exposed links to administrative logins or staff registration.
* Public contact inquiries and appointment scheduling with cascading **Continent → Country** filters.

### B. Client Application Tracking Portal
* **Login Identifier:** Client's **Passport Number** (e.g. `A12345678`).
* **Account Creation:** Client accounts can ONLY be generated by authorized Admin or Staff members. Public client registration is strictly disabled.
* **Temporary Password & Forced Reset:** When created by staff, the client receives a temporary password with `mustChangePassword: true`. On first login, a mandatory security modal intercepts the session and forces a strong password update before granting access.
* **Verified Password Recovery:** Clients can recover their password via Passport Number + matching last 4 digits of their registered phone number.
* **Strict Read-Only Isolation:** Under `/api/v1/client/*`, endpoints are strictly constrained to `req.user.userId`. Clients cannot edit profiles, alter document verification statuses, add processing steps, or view internal staff notes.

### C. Private Employee Portal (Staff & Admin)
* **Access Identifiers:** Employee ID or Official Corporate Email + Password.
* **Two-Factor Authentication (MFA):** Mandatory for all `STAFF`, `ADMIN`, and `SUPER_ADMIN` accounts.
  - Phase 1: Primary credentials check against hashed password.
  - Phase 2: Generation of a 6-digit MFA challenge dispatched to the verified phone/email, validated before issuing the session JWT.
* **Zero Public Staff Registration:** Staff accounts can only be provisioned by Admins through the Admin Console.

## 2. Role Structure & RBAC Matrix

```
SUPER_ADMIN  ──> System configuration, DB administration, all admin permissions
    │
  ADMIN      ──> Staff management, clients, applications, workflows, payments, audit logs
    │
  STAFF      ──> Assigned client cases, step progression, document verification, payments (if permitted)
    │
  CLIENT     ──> Strictly read-only application tracking, documents status, profile viewing
```

### Granular Staff Permissions
Admins assign granular permission arrays to Staff profiles:
* `clients:view`, `clients:create`, `clients:edit`
* `applications:view`, `applications:create`, `applications:edit`, `applications:assign`
* `workflows:manage`, `steps:update`
* `documents:view`, `documents:upload`, `documents:verify`, `documents:download`
* `payments:view`, `payments:create`, `payments:reverse`
* `reports:view`

## 3. Cryptographic Standards & Server-Side Controls

1. **Password Hashing:**
   - Hashed using salt rounds via bcrypt. Plaintext passwords are never logged or stored.
2. **Encryption of Sensitive Identifiers:**
   - National ID numbers (NID) and Passport numbers are encrypted at rest using **AES-256-GCM** with unique initialization vectors (IV) and authentication tags.
   - Display variants are masked: `A12****78` and `199************23`.
3. **Session Management & Expiration:**
   - JSON Web Tokens (JWT) signed with a 256-bit secret key, with automatic 7-day expiration.
   - HTTP-only, `sameSite: 'lax'`, `secure: true` cookies preventing XSS-based token theft.
4. **Session Revocation & Deactivation:**
   - Tokens include unique `sessionId` claims. Logout operations add the session to `revokedSessions`, invalidating all active requests immediately.
   - Every authenticated request verifies `user.isActive`. Deactivated accounts return `403 ACCOUNT_DEACTIVATED` on the very next request.
5. **Brute-Force Protection & Lockout:**
   - 5 consecutive failed login attempts trigger an automatic 15-minute temporary account lockout (`lockedUntil`).
   - Rate limiting enforced on all auth routes: 100 requests per 15-minute window with `authLimiter`.
6. **Server-Side Authorization Enforcement:**
   - Direct API calls are strictly guarded with `requireRole(RoleName.ADMIN, RoleName.STAFF)` and `requirePermission(...)`.
   - Verified via automated tests: A `CLIENT` token attempting `GET /api/v1/clients` or a `STAFF` token attempting `GET /api/v1/audit-logs` immediately receives `HTTP 403 Forbidden`.
